# 依頼書 4.0-10：v3 の形で配置を保存する API と、ページ名

TaPoard 4.0 作り直しの段階5の4回目です。次の 11 で作る**専用の設定ウインドウ**が使う、**v3 の形で配置を読み書きする API** を作ります。あわせて**ページ名**（例：「配信」「作業」）を入れ、4.1 のマクロのために**1つのボタンが操作の並びを持てる形**を設定ファイルに用意します。

## 進め方の考え方（大事）

設定ファイルは 05 から v3 ですが、メモリ上はまだ v2 の `Settings` で動いています（`state.Config` を使う所が 200 か所以上）。これを今いっぺんに v3 に置き換えると、古い画面（`/`・`/settings`）と古い API が壊れます。そこで：

- **10（今回）**：外から見える API と設定ファイルを v3 にそろえる。中では今までどおり v2 に変換して、今ある検証・保存の仕組みを使う（05 からの「少しずつ置き換える」やり方の続き）。
- **14**：古い画面と古い API を消すときに、メモリ上も v3 にして v2 の `Settings` と `DeckLayoutV2` を消す。

## 3. やること

### 3.1 `GET /api/v3/deck`（Admin）

設定ウインドウが編集のために読む API です。

- 返す形：`{ "schemaVersion": 3, "version": "…", "deck": { …v3 の deck 全部… }, "widgetDefinitions": [ … ] }`
- `deck` は `SettingsMigration.ToV3(state.Config).deck` をそのまま（`path`・`args`・`url`・`text`・`hotkey`・`steps` も含む。管理者だけなので）。
- `deck.background` も含める（読むだけ。保存は今の `/api/background…` で行う。3.2 参照）。
- ルート表に `GET /api/v3/deck Admin` を足す。

### 3.2 `POST /api/v3/deck`（Admin）

設定ウインドウが、編集した配置を**まとめて**保存する API です。

- 本文：`{ "baseVersion": "<読んだときの version>", "deck": { …v3 の deck… } }`
- `baseVersion` が今の `state.Version` と違えば **409** `{ "error": "ほかの所で設定が変わりました。読み直してください。", "version": "<今の version>" }`。何も変えない。
- 検証（新しい静的クラス `DeckV3Validator`）：だめなら **400** と、どこが悪いかわかる日本語の `error`（例：「横向き 2ページ目の『配信開始』が枠からはみ出しています」）。
  - 列・行は 2〜8。ページは向きごとに 1〜`DeckLayout.MaxPages`（今は 40）。ボタンは向きごとに 40 個まで（今と同じ上限）。id の重複なし。
  - 各ボタンが枠の中に収まり、ボタン同士・フェーダーと重ならない。大きさがその type で使える大きさ（`WidgetRegistry`）。
  - 各ボタンの中身は今の `ValidateEntry` と同じ検査（名前・アイコン・type ごとの項目）。**同じ検査を2回書かない**：`ValidateEntry` を v2 の `AppEntry` に変換したものに対して呼ぶ形でよい。
  - フェーダーの位置・大きさ（今の `/api/layout` と同じ範囲）。
  - ページ名（3.3）と操作の並び（3.4）の検査。
  - **サーバーはボタンを勝手に動かさない。** v2 に変換して今の `DeckLayout.Validate` を通したあと、位置が1つでも変わっていたらエラーにする（黙って並べ直さない）。
- 保存：
  - `security`・`weather`・`pcWindow` と **`deck.background`** は今のサーバーの値を残す（本文の値は使わない。背景は画像ファイルと一緒に `/api/background…` で管理しているため）。
  - アプリのアイコン（exe から取った `icon`）など、今 `KeepServerFields` で残しているボタンごとのサーバー側の値も残す。`KeepServerFields` を「全体の値」と「ボタンごとの値」に分けて、ボタンごとの方を両方の保存で使う。
  - そのあとは今の `SaveSettings` と同じ流れ（`state.Config` を入れ替え、`DisplaySubscriptions.RemoveUnknown`、`InputSessions.ClearAll`、`state.Save()`、新しい `Version`、ページ番号を範囲内に、`Signal`）。**この流れは1つのメソッドにまとめて、`SaveSettings` と `POST /api/v3/deck` の両方から呼ぶ。**
  - ページ削除のやり直し（`PageUndo`）は、v3 で保存したら消す（古い操作のやり直しで新しい配置を戻さないため）。
- 返す形：`{ "ok": true, "version": "<新しい version>" }`
- 本文の上限は今の 2MB のまま。
- ルート表に `POST /api/v3/deck Admin` を足す（ルートは 48 本になる）。

### 3.3 ページ名

- v3：`PageV3` に `public string name { get; set; }` を足す。
- v2（メモリ上の今の形）：`Settings` に `landscapePageNames`・`portraitPageNames`（`List<string>`、ページ番号の順）を足し、`ToV3`/`ToV2` で引き継ぐ。足りない所は空、余った所は捨てる。
- 決まり：前後の空白を取る、改行なし、**20 文字まで**、空でもよい（空なら画面では数字だけ）。
- 今のページ移動・削除・削除のやり直し（`PageController` の `MovePage`・`DeletePage`・`UndoDeletePage`）と、ページを増やす・減らす所で、**名前もページと一緒に動く**こと。
- スマホ向けの `/api/v3/state`（`PublicDeckV3`）にも `name` を出す（ページ名は見せてよい）。
- 古い `/api/state` には出さない（古い画面は変えない）。

### 3.4 操作の並び（4.1 のマクロの置き場所）

4.1 で「1つのボタンで複数の操作を順に実行する」マクロを作ります。今回は**設定ファイルに置き場所を作って、読み書きと検査ができるところまで**です。実行はしません。

- 新しいクラス `ActionStep`（`src\ActionSteps.cs`）：`type`（今のボタンの type のうち `app`・`hotkey`・`url`・`clipboard`・`audioDevice`）、`action`、`category`、`path`、`args`、`url`、`text`、`hotkey`、`deviceId`、`deviceTarget`、`delayMs`（この操作の前に待つミリ秒）。
- `DeckItem.steps`（`List<ActionStep>`、なければ `null`）と、v2 の `AppEntry.steps` を足して `ToV3`/`ToV2` で引き継ぐ。
- 検査（静的クラス `ActionSteps.Validate`）：20 個まで、`delayMs` は 0〜10000、各操作は今のボタンの検査と同じ規則（`ValidateEntry` の type ごとの部分を、`ActionStep` にも使える形に分ける。同じ検査を2回書かない）。
- **今は `steps` を持てる type はまだ無い**ので、`steps` が付いたボタンは保存でエラーにする（「操作の並びは 4.1 で使えるようになります」）。テストでは `ActionSteps.Validate` を直接呼んで確かめる。
- スマホには出さない（`PublicDeckV3` は許可リストなので出ないはず。テストで確かめる）。

### 3.5 ページ名を画面に出す

- スマホ（`TopBar`）：名前があれば「配信　1 / 3」、なければ今の「1 / 3」。長い名前は省略記号。
- PC ウインドウ：今の `page:<n>/<m>` はそのまま送り、**新しく `pagename:<名前>` を送る**（名前が変わったときだけ。空なら `pagename:`）。
  - C#（`PcWindow.cs`）：`PageRequest` で `pagename:` を受けたら、帯のページ表示の左に名前を出す（`SetPageName`。幅が足りなければ省略記号）。`CanTurn` などは今の `page:` のまま。これ以外の `PcWindow` の動きは変えない。

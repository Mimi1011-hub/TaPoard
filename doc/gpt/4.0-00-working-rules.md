# 4.0 の作業の決まり（すべての依頼書に共通）

使用量を減らし、レビューしやすくするための決まりです。各依頼書の「必ず守ること」と一緒に守ってください。

## 1. ファイルの直し方

- **ファイルを丸ごと書き直さない。** 変える行の前後だけを置き換える（パッチ・部分置換）。`Set-Content` や「ファイル全体を出力して保存」で既存のファイルを上書きしない。新しいファイルを作るときだけ全体を書いてよい。
- 改行は **LF** のまま。CRLF に変えない（リポジトリの `.gitattributes` でも LF にそろえる）。文字コードは UTF-8（BOM なし）。
- **1行に文をいくつも詰めない。** 1行に1つの文、1行は 160 文字まで（JSON の言語ファイルは 1行に1キー）。「300 行まで」を守るために行をつなげない。300 行を超えそうなら、役割でファイルを分ける。
- 変えたら `git diff --stat` を見て、**直した量より大きな差分が出ていないか**確かめる（数千行の差分が出たら、改行や丸ごと書き直しになっている）。

## 2. 読み方

- **`web\app.js`（約8000行）や `src\PcWindow.cs`（約2000行）を最初から全部読まない。** 依頼書に書いた関数名で検索（`Select-String` / `rg`）して、その前後だけ読む。
- 一度読んだファイルを何度も読み直さない。

## 3. 進め方

- 依頼書の「やること」の **1項目ごとに commit** する（途中で使用量の上限が来ても、そこまでが残るように）。
- 作業中は**直した所に関係するテストだけ**動かす（例：`tests\bin` に1本だけビルドして実行、`node tests\v4-phone-ui.cjs` だけ）。`run-unit.ps1 -UI` と `test.ps1` は最後に1回。
- テストが落ちたら、まず落ちたテストの出力の最後の数十行だけを見る。
- 上限が近くなったら、そこまでを commit して止め、「どこまでできたか・次に何をするか」を報告に書く。

## 4. 報告とチャット

- **1つの依頼書につき1つの新しいチャット**で始める。前の依頼書のチャットの続きでやらない。
- 途中報告はしない（上限で止まるときだけ、どこまでできたかを書く）。最後に短い要約だけ出す。
- テストの出力は**最後の10行だけ**報告する。全部貼らない。
- 依頼書の「対象ファイル」に書いた所だけ読む。書いていない所が必要になったら、検索して前後だけ読む。

## 5. 画面のテスト（Playwright）

- 画面のテストを動かす前に、前のテストで残ったブラウザや TaPoard の処理が残っていないか確かめ、残っていたら止める（例：`Get-Process msedge, TaPoard -ErrorAction SilentlyContinue`）。残ったままだと次のテストとぶつかって失敗し、やり直しで使用量が増える。
- 画面のテストは1本ずつ順番に動かす。同時に動かさない。
- 画面に出る文字は、C# は `Text.Get`、Web は `i18n`。コードに日本語の文を書かない。

